## 1. High-Level Architecture: Mobile vs Desktop

### 1A. Mobile Flutter App (`./clients/mobile`, Dart-only)

#### State Management: **Riverpod**

**Rationale:**

-   **API-heavy nature**: Riverpod excels at managing async data fetching, caching, and error states
-   **Type-safe dependencies**: Compile-time safety for dependency injection
-   **Testability**: Easy to mock repositories and services for testing
-   **Reactive updates**: Automatic UI rebuilds when state changes
-   **Scoped providers**: Perfect for managing auth state, API clients, and feature-specific state
-   **Future/Stream providers**: Natural fit for API calls and streaming chat responses

**Alternative considered**: Bloc/Cubit - More boilerplate, but Riverpod's async providers are more ergonomic for HTTP-based apps.

#### Navigation: **go_router**

**Rationale:**

-   **Declarative routing**: Type-safe route definitions
-   **Deep linking**: Built-in support for URLs and deep links
-   **Auth guard integration**: Easy to wrap routes with auth checks using `Redirect` widgets
-   **Nested routing**: Supports complex navigation hierarchies
-   **State preservation**: Better than Navigator 2.0 for complex apps

**Route Structure:**

```
/ (splash/loading)
  /login
    /login/local (username/password)
    /login/oidc (OIDC provider selection)
  /callback (OIDC callback handler)
  /app (authenticated routes)
    / (chat list)
    /chat/:chatId (chat detail)
    /settings
      /profile
      /api-keys
      /models
```

#### Networking Stack: **dio**

**Rationale:**

-   **Interceptor support**: Clean separation for auth header injection and error handling
-   **Response/Request transformers**: Easy JSON serialization/deserialization
-   **CancelToken**: Better than http package for canceling requests
-   **Timeout configuration**: Built-in timeout support
-   **Cookie management**: Useful for session handling if needed
-   **Multi-part uploads**: Essential for file uploads

**Layering Strategy:**

1. **Interceptor Layer** (`lib/core/network/interceptors/`):

    - `AuthInterceptor`: Adds `Authorization: Bearer <token>` header
    - `ErrorInterceptor`: Converts HTTP errors to domain errors
    - `LoggingInterceptor`: Request/response logging (dev only)

2. **API Client Layer** (`lib/core/network/api_client.dart`):

    - Base `Dio` instance with interceptors
    - Configurable base URL
    - Error handling utilities

3. **Repository Layer** (`lib/data/repositories/`):
    - Implements abstract repository interfaces
    - Uses API client for HTTP calls
    - Handles JSON serialization/deserialization

#### API Endpoint Mapping (from `server/src/api/`)

**Authentication:**

-   `POST /api/auth/local/login` → `AuthRepository.login()`
-   `GET /api/auth/config` → `AuthRepository.getAuthConfig()` (OIDC enabled?)
-   `GET /api/auth/login` → OIDC flow (redirect)
-   `GET /api/auth/callback` → OIDC callback handler
-   `POST /api/auth/logout` → `AuthRepository.logout()`
-   `GET /api/auth/me` → `AuthRepository.getCurrentUser()`

**Chats:**

-   `GET /api/chats` → `ChatRepository.listChats(page?, pageSize?)`
-   `POST /api/chats` → `ChatRepository.createChat(title?, modelProvider, modelId)`
-   `GET /api/chats/{id}` → `ChatRepository.getChat(id)`
-   `PUT /api/chats/{id}` → `ChatRepository.updateChat(id, title?)`
-   `DELETE /api/chats/{id}` → `ChatRepository.deleteChat(id)`
-   `GET /api/chats/{id}/messages` → `ChatRepository.getMessages(chatId)`

**Chat Completion:**

-   `POST /api/chat` → `ChatRepository.sendMessage()` (non-streaming)
-   `POST /api/chat/stream` → `ChatRepository.streamMessage()` (SSE streaming)

**User:**

-   `GET /api/me` → `UserRepository.getProfile()`
-   `PUT /api/me` → `UserRepository.updateProfile()`

**Models:**

-   `GET /api/models` → `ModelsRepository.listModels()`
-   `GET /api/config/models` → `ModelsRepository.getAvailableModels()`

### 1B. Desktop Flutter + Rust App

#### Architecture Overview

**Rust Core (`t3chat_core/`):**

-   Domain models (User, Chat, Message, etc.)
-   HTTP client (reqwest with async/await)
-   API client methods (login, list chats, send message, stream responses)
-   Token storage and refresh logic
-   Optional: Local caching (SQLite) for offline support

**Dart (Flutter Desktop):**

-   UI widgets and screens
-   Navigation (go_router, same as mobile)
-   State management (Riverpod, same as mobile)
-   Thin repository implementations that call Rust via FFI
-   Platform-specific integrations (file system, native dialogs)

#### FFI Mechanism: **flutter_rust_bridge**

**Rationale:**

-   **Code generation**: Generates Dart bindings from Rust code
-   **Type safety**: Automatically converts Rust types to Dart types
-   **Async support**: Supports async Rust functions (returns Dart Futures)
-   **Streaming support**: Can expose Rust streams as Dart Streams (for SSE)
-   **Error handling**: Automatic error conversion
-   **Maintenance**: Active project, well-documented

**Alternative considered**: Manual FFI with `dart:ffi` - Too much boilerplate, error-prone.

## 2. Shared vs Separate Parts

### 2A. Conceptual Sharing

**Must be conceptually shared:**

1. **Auth Flows:**

    - Login/logout state machine
    - Token storage and retrieval
    - Token refresh logic (if server supports refresh tokens)
    - OIDC flow steps (initiate, callback, token extraction)

2. **Data Models:**

    - `User`: id, email, name, username, avatar_url, roles
    - `Chat`: id, user_id, title, model_provider, model_id, created_at, updated_at
    - `Message`: id, chat_id, role, content, created_at, tokens_used, model_used
    - `Model`: id, name, provider, etc.
    - `Preset`, `Agent`, etc.

3. **API Semantics:**

    - Endpoint paths (e.g., `/api/auth/local/login`, `/api/chats`)
    - Request/response shapes (from `server/src/api/*/mod.rs`)
    - Error codes (401 = unauthorized, 403 = forbidden, 404 = not found)
    - Pagination (page, page_size query params)

4. **Chat State Machine:**
    - States: `idle`, `loading`, `sending`, `streaming`, `error`
    - Transitions: user sends message → `sending` → `streaming` → `idle` (or `error`)

### 2B. Practical Sharing Strategy

## 3. Authentication Design

### 3A. Auth Flows

#### Local Username/Password Auth

**Endpoint**: `POST /api/auth/local/login` (from `server/src/api/auth/mod.rs`)

**Request:**

```json
{
    "username": "admin",
    "password": "P@$$w0rd"
}
```

**Response:**

```json
{
    "token": "eyJhbGciOiJIUzI1NiIs...",
    "expires_at": 1234567890,
    "user": {
        "id": "user-id",
        "email": "admin@localhost",
        "name": "Admin User",
        "username": "admin",
        "roles": ["admin"]
    }
}
```

**Flow:**

1. User enters username/password
2. Client calls `POST /api/auth/local/login`
3. Server validates credentials, returns JWT token
4. Client stores token securely (Keychain/Keystore)
5. Client includes token in `Authorization: Bearer <token>` header for subsequent requests

#### OIDC Authentication (Optional)

**Endpoint**: `GET /api/auth/config` returns `{ "oidc_enabled": true/false }`

**Flow:**

1. Client checks `GET /api/auth/config` to see if OIDC is enabled
2. If enabled, show OIDC login button
3. User clicks OIDC button → Client opens browser/webview to `GET /api/auth/login`
4. Server redirects to OIDC provider (Google, Auth0, etc.)
5. User authenticates with provider
6. Provider redirects to `GET /api/auth/callback?code=...&state=...`
7. Server exchanges code for tokens, creates/finds user, generates JWT
8. Server redirects to frontend: `{FRONTEND_URL}/auth/callback?token=<jwt>`
9. Client extracts token from URL, stores it securely
10. Client navigates to main app

**Mobile Considerations:**

-   Use `url_launcher` or `webview_flutter` for OIDC flow
-   Handle deep link callback (e.g., `myapp://auth/callback?token=...`)

**Desktop Considerations:**

-   Use system browser (`url_launcher`) or embedded webview
-   Handle callback URL (custom protocol handler or localhost redirect)

### 3B. Token Handling

#### Mobile (Dart)

**Storage:**

-   Use `flutter_secure_storage` package
-   Stores tokens in Keychain (iOS) / Keystore (Android)
-   Keys: `access_token`, `refresh_token` (if applicable)

**Header Injection:**

-   `AuthInterceptor` (dio interceptor) reads token from secure storage
-   Adds `Authorization: Bearer <token>` to all requests
-   Handles token refresh (if server supports refresh endpoint)

**401/403 Handling:**

-   `ErrorInterceptor` catches 401/403 responses
-   Clears token from storage
-   Redirects to login screen
-   Optionally: Attempt token refresh if refresh token exists

#### Desktop (Rust Core)

**Decision: Rust Core Owns HTTP + Tokens**

**Rationale:**

-   **Security**: Tokens never leave Rust (no Dart ↔ Rust token passing)
-   **Consistency**: All HTTP logic in one place (Rust)
-   **Simplicity**: Dart only needs to call FFI functions; Rust handles auth
-   **Performance**: Fewer FFI calls (Rust batches requests with token)

**Implementation:**

```rust
// t3chat_core/src/api/client.rs
pub struct ApiClient {
    client: reqwest::Client,
    base_url: String,
    token_storage: TokenStorage,
}

impl ApiClient {
    pub async fn login(&self, username: String, password: String) -> Result<UserAndToken> {
        let response = self.client
            .post(&format!("{}/api/auth/local/login", self.base_url))
            .json(&json!({"username": username, "password": password}))
            .send()
            .await?;

        let data: LocalLoginResponse = response.json().await?;
        self.token_storage.save_token(data.token.clone()).await?;
        Ok(UserAndToken { user: data.user, token: data.token })
    }

    pub async fn request(&self, method: Method, path: &str) -> Result<reqwest::Response> {
        let token = self.token_storage.get_token().await?;
        self.client
            .request(method, &format!("{}{}", self.base_url, path))
            .bearer_auth(token)
            .send()
            .await
    }
}
```

**Token Storage (Rust):**

-   Use `keyring` crate for secure storage (Keychain/Windows Credential Manager/Linux Secret Service)
-   Keys: `t3chat_access_token`, `t3chat_refresh_token`

**401 Handling:**

-   Rust API client catches 401 responses
-   Clears token from storage
-   Returns `FfiError::Auth("Unauthorized")` to Dart
-   Dart repository implementation catches error, navigates to login

**Refresh Token (if server supports):**

-   Rust API client checks token expiry before requests
-   If expired, calls `POST /api/auth/refresh` (if OIDC)
-   Updates stored token
-   Retries original request

#### Repository Interface Integration

```dart
// domain/repositories/auth_repository.dart
abstract class AuthRepository {
  Future<UserAndToken> login(String username, String password);
  // Rust implementation: Calls FFI, Rust handles HTTP + token storage
  // Dart implementation: Calls HTTP directly, Dart handles token storage
}
```

**Trade-offs for T3Chat:**

| Aspect      | Rust-Owned (Desktop)            | Dart-Owned (Desktop)                   |
| ----------- | ------------------------------- | -------------------------------------- |
| Security    | ✅ Tokens never leave Rust      | ⚠️ Tokens passed via FFI               |
| Simplicity  | ✅ Dart just calls FFI          | ⚠️ Dart manages tokens, passes to Rust |
| Performance | ✅ Fewer FFI calls              | ⚠️ Token passed on every request       |
| Consistency | ✅ All HTTP in Rust             | ⚠️ Split between Dart and Rust         |
| Flexibility | ⚠️ Harder to debug token issues | ✅ Dart can inspect tokens             |

**Decision: Rust-Owned** - Better security and performance for desktop.

#### Streaming Logic

```dart
// data/repositories/chat_repository_impl.dart
@override
Stream<ChatMessageEvent> streamMessage(
  String chatId,
  String content, {
  required String modelProvider,
  required String modelId,
}) async* {
  final response = await _dio.post(
    '/api/chat/stream',
    data: {
      'chatId': chatId,
      'message': content,
      'modelProvider': modelProvider,
      'modelId': modelId,
      'stream': true,
    },
    options: Options(
      responseType: ResponseType.stream,
    ),
  );

  final stream = response.data.stream.transform(utf8.decoder)
    .transform(const LineSplitter())
    .where((line) => line.startsWith('data: '))
    .map((line) => line.substring(6))
    .where((data) => data.isNotEmpty && data != '[DONE]');

  String buffer = '';
  for await (final chunk in stream) {
    if (chunk == STREAM_END_MARKER) {
      yield ChatMessageEvent.done();
      break;
    }
    try {
      final json = jsonDecode(chunk);
      buffer += json['delta'] as String? ?? '';
      yield ChatMessageEvent.chunk(delta: json['delta'] ?? '');
      if (json['done'] == true) {
        yield ChatMessageEvent.done();
        break;
      }
    } catch (e) {
      // Skip invalid JSON
    }
  }
}
```

## 7. Desktop-Specific Considerations

### 7A. FFI Overhead

**Where it Matters:**

-   Chat streaming (many small chunks)
-   Real-time UI updates (message list scrolling)

**Mitigation:**

1. **Batch FFI Calls:**

    - Rust streams return chunks, not individual characters
    - Dart accumulates chunks before UI updates (debounce/throttle)

2. **Use Async Streams:**

    - `flutter_rust_bridge` supports async streams
    - No blocking FFI calls

3. **Background Processing:**
    - Rust handles HTTP in background thread
    - FFI calls are async (non-blocking)

**Example (Streaming):**

```rust
// Rust streams chunks (not per-character)
pub fn ffi_stream_chat(...) -> Stream<FfiChatChunk> {
    // Returns chunks of ~100-1000 chars, not single chars
}
```

```dart
// Dart debounces UI updates
Stream<ChatMessageEvent> streamMessage(...) {
  return _rust.ffiStreamChat(...)
    .debounceTime(Duration(milliseconds: 50)) // Batch updates
    .map((chunk) => ChatMessageEvent.chunk(delta: chunk.delta));
}
```

### 7B. Local Persistence

**Option 1: Rust SQLite Cache**

**Pros:**

-   All persistence logic in Rust
-   Can cache API responses
-   Offline support (future)

**Cons:**

-   More Rust code
-   FFI for cache queries

**Option 2: Dart SQLite/Hive**

**Pros:**

-   Easier to implement (Flutter packages)
-   UI can query cache directly

**Cons:**

-   Split persistence (Rust HTTP, Dart cache)
-   Duplication risk

**Recommendation: Start with Dart (Hive/SQLite)**

-   Simpler for MVP
-   Can move to Rust later if needed
-   Use for: token storage (but Rust handles this), chat history cache, user preferences

**Token Storage: Rust (via keyring)**

-   Secure storage in Rust
-   No FFI overhead (Rust owns HTTP)

**Cache: Dart (Hive)**

-   Simple key-value store
-   Cache chat list, messages
-   Invalidate on app start / refresh
